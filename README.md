# ГШП Оперативка

Внутреннее веб-приложение, заменяющее Excel-процесс «оперативки»: руководители заполняют свои позиции,
куратор их собирает и проверяет, руководство получает финальную версию. Актуальное ТЗ — [TZ_v4.md](./TZ_v4.md)
(раздел про отказ от подразделений — в начале файла); история решений — [ANALYSIS.md](./ANALYSIS.md).
Старое ТЗ [TZ.md](./TZ.md) сохранено для истории.

## Стек

Next.js 16 (App Router) + React 19 + TypeScript + Prisma 6 + PostgreSQL (Neon) + Tailwind CSS 4 + Zod + Vitest.

## Роли

| Роль | Что может |
|---|---|
| Руководитель (`HEAD`) | видит все позиции, создаёт и правит только свои (где он «Ответственный»), удаляет свои |
| Куратор (`CURATOR`) | видит и правит всё, назначает ответственных, ведёт цикл оперативки, колонки, треки, ответственных; чужие позиции не удаляет |
| Руководство (`MANAGEMENT`) | видит только финальные оперативки |
| Администратор (`SYSTEM_ADMIN`) | пользователи, справочники, читает таблицу; в рабочем процессе не участвует |

Права проверяются на сервере на каждый запрос (`lib/permissions.ts`, `lib/session.ts`), интерфейс их только отражает.

## Быстрый старт

```bash
npm install                 # postinstall выполнит prisma generate
cp .env.example .env        # укажите DATABASE_URL и AUTH_SECRET
npx prisma migrate deploy   # применить миграции
npm run db:seed             # справочники: сегменты, статусы, привлекательность
npm run dev
```

Для Neon через pooler в `DATABASE_URL` нужны параметры `?sslmode=require&connect_timeout=30&pgbouncer=true`.

Первый вход: администратор создаётся отдельно (пароль в репозиторий и в чат не попадает):

```bash
ADMIN_EMAIL=admin@example.com ADMIN_PASSWORD='длинный-пароль' ADMIN_NAME='Администратор' npm run create-admin
```

Остальных пользователей создаёт администратор (или куратор — «Ответственные») в «Настройках». Куратор также назначает руководителя куратором и снимает других кураторов (нельзя снять себя и последнего куратора); имя, пароль и отключение куратора остаются у администратора.
Стартовые учётные записи, созданные при переносе данных, имеют временный пароль `ChangeMe123!` — его нужно сменить.

## Скрипты

| Команда | Что делает |
|---|---|
| `npm run dev` / `build` / `start` | разработка / сборка / запуск |
| `npm run test` | юнит-тесты (быстрые, без базы) |
| `npm run test:e2e` | e2e-проверка API на реальной базе (см. ниже) |

## Тесты

* **Юнит-тесты** (`lib/*.test.ts`): права, фильтры и сортировка, поиск, журнал, цикл, свои колонки, валидация.
* **e2e API** (`e2e/api.e2e.ts`, `npm run test:e2e`): вызывает настоящие маршруты `app/api/**` от имени разных ролей
  (сессия подменяется, пароли не нужны). Работает на реальной базе из `.env`: все данные помечаются `E2E<время>`
  и удаляются по завершении, общий вид колонок восстанавливается. Активный цикл оперативки в базе тест не трогает
  (часть про цикл пропускается, если он есть). Запуск занимает несколько минут из-за задержек до удалённой базы;
  упавшие из-за обрыва соединения тесты повторяются автоматически.

## Что есть в приложении

* **Таблица** (`/table`) и **архив** (`/archive`): список сегментов слева (можно выбрать несколько), фильтры с выбором нескольких значений,
  сортировка, поиск, экспорт (CSV/Excel/PDF), панель аналитики выборки и панель «История изменений» (иконка в тулбаре, фильтры «Кто» и «Поле»).
* **Поиск** (`lib/search.ts`): несколько слов сразу, регистр и «ё/е» не важны, ищет по задаче, комментарию, оценке, треку, сегменту,
  ответственному, статусу, привлекательности (код и пояснение), дедлайну и своим колонкам; найденное подсвечивается.
* **Карточка позиции**: правка с контролем версий (конфликт → 409), история «кто что изменил», удаление (архив) и возврат.
* **Оперативка** (`/operativka`): цикл `OPEN → IN_REVIEW → FINAL`, отправка позиций куратору (галка «Опер»), возврат с комментарием,
  напоминание кураторам за 2 дня до срока, неизменяемый финальный снимок, выгрузка финала (CSV/Excel/PDF/PowerPoint),
  пометка «изменено после отправки». Руководство видит только финалы.
* **Посмотреть как руководитель** (куратор): в меню пользователя выбираете руководителя — меню, кнопки и права показываются как у него, запись отключена (сессия остаётся куратора).
* **Настройки** (куратор и администратор): общий вид колонок таблицы (показ, порядок, подписи, удаление стандартных колонок,
  свои колонки нескольких типов), ответственные, треки; у администратора ещё пользователи и справочники.

## Данные и миграции

* Миграции — `prisma/migrations`. Применять `npx prisma migrate deploy`; при изменении схемы сначала `npm run backup-db`.
* Удаление — это архивирование (`archivedAt`); журнал изменений (`AuditEvent`) только дописывается.
* Файлы с реальными данными (`source-data/`, `backups/`) в репозиторий не добавляются.

## Публикация

Репозиторий подключён к Vercel: каждый push в `master` собирает новую версию. На Vercel нужны переменные окружения
`DATABASE_URL` и `AUTH_SECRET` (вносятся вручную в настройках проекта). Миграции применяются к базе отдельно (`prisma migrate deploy`).

## Оперативка как отчёт и шаблоны экспорта

Один движок отчёта — три способа показать. Конфигурация (`lib/report-config.ts`: колонки, группировка до 3 уровней, фильтры, сортировка, режим комментариев) → `buildReport` (`lib/report.ts`) → единая модель (сводка по статусам + дерево Сегмент → Трек → задачи). Экран «Оперативка» и файлы Excel / PDF / CSV / PowerPoint рисуют одну и ту же модель, поэтому вид на экране и в выгрузке совпадает.

- Шаблон = сохранённая конфигурация. Из коробки: «Оперативка по дирекции» и «Как в таблице» (в коде). Личные и общие шаблоны — в таблице `ReportTemplate`; общие создаёт и правит куратор/администратор.
- Финальные оперативки строятся тем же движком из снимка цикла (`buildFinalModel`), доступны и руководству.
- Дирекция пока одна (название в настройке `directorate.name`); выбор дирекции при входе — следующий шаг, в конфиге зарезервировано `directorateId`.

API: `POST /api/report`, `GET /api/export/report?format=&templateId=|config=`, `GET|POST /api/report-templates`, `PATCH|DELETE /api/report-templates/[id]`, `POST /api/cycles/[id]/report`, `GET /api/cycles/[id]/export?config=|templateId=`.

## Дирекции и роли

Иерархия: **руководитель направления → директор дирекции → ЗГД**; **админ** заводит дирекции и людей и назначает директоров и ЗГД.

| Роль | Значение в коде (в базе) | Что видит и может |
|---|---|---|
| Руководитель | `HEAD` | позиции своей дирекции; правит только свои |
| Директор | `DIRECTOR` | всё в своей дирекции: правит все позиции, ведёт цикл, отправляет итог, ведёт руководителей, сегменты, треки, колонки, общие шаблоны |
| ЗГД | `EXECUTIVE` (`MANAGEMENT`) | только отправленные итоги всех дирекций |
| Админ | `ADMIN` (`CURATOR`) | то же, что директор, в любой дирекции (переключатель в шапке) + дирекции, роли, статусы, привлекательность |
| Технический администратор | `SYSTEM_ADMIN` | как раньше: читает позиции, ведёт пользователей |

- Дирекция принадлежит данным: `directorateId` у пользователей, позиций, сегментов, треков, циклов, своих колонок и общих шаблонов; раскладка таблицы — настройка `table.columns:<id дирекции>`. Статусы и привлекательность общие.
- **Границы проверяются на сервере**, в одном месте (`lib/scope.ts`): запросы к данным всегда получают дирекцию из сессии (`requireActor` → `directorateId`; у админа — из куки выбора). Чужая запись по идентификатору «не существует» (404). Изоляцию проверяют e2e-тесты с двумя дирекциями.
- Новые значения ролей `ADMIN`/`EXECUTIVE` в базе хранятся старыми именами (`@map`), поэтому старая и новая версии приложения работают с одной базой.
- API: `GET|POST /api/directorates`, `PATCH /api/directorates/[id]`, `POST /api/directorates/select`.

## Локальная база и выкладка

Разрабатываем на **локальной базе** (настоящий PostgreSQL, запускается из проекта, ничего ставить не нужно), а боевую (Neon) трогаем только при выкладке. Так работа не зависит от интернета, а тесты идут за секунды.

- `.env` — локальная база (`postgresql://postgres:postgres@localhost:54329/tasksflot`). `.env.neon` — адрес боевой (в git не попадает).
- **Каждый день:** `npm run db:local` (окно оставить открытым), затем `npm run dev`.
- **Первый раз или чтобы освежить данные:** `npm run db:pull` — копирует данные боевой базы в локальную (боевая только читается; локальные данные заменяются).
- **Новые миграции** при разработке: `npx prisma migrate dev` (применяются к локальной базе).
- **Тесты:** `npm run test` и `npm run test:e2e` — второй идёт по локальной базе.
- **Выкладка:** 1) `npm run db:prod:migrate` — применить новые миграции к боевой базе; 2) `git push` — Vercel соберёт новую версию. Миграции проекта только добавляют, поэтому между шагами старая версия сайта продолжает работать.
